Benchmark Demo Components Architecture
Demo Objective

The story is simple: run the same five-service workload twice. First start the application in traditional client-side pooling mode, where each service initializes its own dedicated database sessions according to poolMin. Then restart the application in DRCP mode, where services avoid per-service minimum idle sessions and borrow database-resident pooled servers. The proof is the dashboard's live database footprint: V$SESSION.SERVER = DEDICATED for traditional mode versus V$CPOOL_STATS.NUM_OPEN_SERVERS for DRCP when available.

The comparison is meaningful only when the same workload parameters are used in both runs: same concurrency, duration, and service mix. Each benchmark run is persisted in Oracle Database, so the Results tab can compare runs even after restarting the application.

Before You Start
  • Open the Benchmark page and confirm that the current application mode is shown at the top.
  • Check that Database footprint and Reserved vs Actually Used are updating.
  • Use the same Concurrency, measured duration, warm-up, and weighted service mix for both runs.
  • Recommended baseline: Warm-up=10s, Concurrency=6, Measured duration=45s.
  • Traditional pools are configured with TRADITIONAL_POOL_MIN=5 and TRADITIONAL_POOL_MAX=8 for the validated ADB PRO demo environment.
  • DRCP client pools are configured with DRCP_POOL_MIN=0 and DRCP_POOL_MAX=8; the shared database-resident pool uses DRCP_RESIDENT_MIN=2 and DRCP_RESIDENT_MAX=8.
  • The configured connection envelope is 40 sessions, matching 5 services x TRADITIONAL_POOL_MAX=8. It is a presentation guardrail, not the Oracle Database maximum.
  • Stop any prior load run and wait a few seconds for the live session table to settle.

Why DRCP Should Use Fewer Connections

Traditional mode creates one node-oracledb pool per service: min 5 and max 8. With five services, that means 25 idle dedicated database sessions after pool initialization and up to 40 client-side capacity. DRCP mode avoids that per-service minimum idle footprint by using DRCP_POOL_MIN=0 in the client tier and attaching requests through a pooled TNS alias to database-resident pooled servers configured with the conservative 2/8 sizing idea. The comparison is about idle/open database footprint and server-process reuse, not database saturation.

Traditional path:
5 service pools x poolMin 5 -> 25 dedicated sessions
5 service pools x poolMax 8 -> up to 40 client-side capacity
configured connection envelope -> 40 sessions, matching 5 service pools x poolMax 8

DRCP path:
5 service pools x client poolMin 0 -> no per-service minimum idle sessions
shared database-resident pool -> reusable pooled database servers
If the Reduction Is Not Obvious
  • Confirm both runs used the same warm-up, concurrency, measured duration, and service mix.
  • Confirm the dashboard stayed open from the traditional run through the DRCP run.
  • Run traditional first, then DRCP. The comparison table is designed for that story.
  • Wait a few refresh cycles; metrics are sampled periodically from the database.
  • Check the Recent Requests table to confirm the active mode.
  • Remember that existing idle pooled sessions may remain visible; compare peaks under load, not just a single idle sample.
Why DRCP Current Comes From V$CPOOL_STATS

DRCP_POOL_MIN=0 is the client-side choice that avoids recreating the traditional idle footprint in Node. The database-side DRCP pool has its own shared open-server footprint. The dashboard reads V$CPOOL_STATS.NUM_OPEN_SERVERS for DRCP current when available. If V$CPOOL_STATS is not visible in this Autonomous Database environment, the dashboard falls back to V$SESSION.SERVER = POOLED, which is less complete for idle/open DRCP capacity.

One-Minute Talk Track

"We start with the traditional model. Each retail service has an isolated schema and its own client-side connection pool. We configured min 5, max 8 per service for this ADB PRO demo, so initializing five service pools creates about 25 idle dedicated database sessions before the workload needs them. Now we switch to DRCP. The services are still isolated, but the client tier does not reserve minimum idle sessions per service; requests use reusable pooled database servers inside Oracle. The dashboard proves the change from database views: traditional is counted from V$SESSION dedicated sessions, while DRCP current is counted from V$CPOOL_STATS.NUM_OPEN_SERVERS when visible."
