What DRCP Is Doing

DRCP moves reusable server processes into Oracle Database. The client tier borrows from that resident pool using the pooled TNS alias, so the database can serve many mid-tier processes with fewer open server processes.

traditional alias -> dedicated database sessions
pooled alias      -> SERVER=POOLED database sessions
resident pool     -> reusable database server processes

traditional proof -> V$SESSION.SERVER = DEDICATED
DRCP proof        -> V$CPOOL_STATS, V$CPOOL_CONN_INFO,
                    V$CPOOL_CC_INFO, V$SESSION fallback
Why Connection Classes Matter

Connection classes keep reuse aligned with the service that requested the session. Catalog, inventory, orders, payments, and customers share the resident pool infrastructure, but each class can preserve the right reuse boundary and attribution.

Connection Classes

One class per service keeps reuse organized. Services share the resident pool, but catalog, orders, payments, inventory, and customers still get clear reuse boundaries.

Connection Tagging

Tags describe reusable session state such as service, region, and role. A matching tag avoids unnecessary session setup work on the next checkout.

Session Purity

POOLED favors fast reuse. NEW asks Oracle for cleaner state when strict isolation is more important than maximum reuse.

Session State Fix-up

After checkout, the backend sets module, action, client identifier, and the requested tag. This keeps dashboard attribution clear without relying on a pool callback.

Monitoring

The dashboard uses V$SESSION.SERVER = DEDICATED for traditional sessions and V$CPOOL_STATS.NUM_OPEN_SERVERS for DRCP open servers when available. If the DRCP pool view returns no rows, it falls back to V$SESSION.SERVER = POOLED.

Service Isolation

Each service connects only to its own schema. Cross-service consistency is maintained through shared business IDs, not cross-schema table access.
